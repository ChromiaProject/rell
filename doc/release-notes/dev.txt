UNRELEASED NOTES

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
1. Tools: Linter reports if-expression chains for rule_replace_if_with_when

The rule_replace_if_with_when inspection only looked at if statements, so a chain of if and else-if branches in
expression position went unreported:

    val b = if (a == 1) 1 else if (a == 2) 0 else 3;

Such chains are now reported like their statement counterparts, and the quick-fix rewrites them as a when
expression:

    val b = when {
        a == 1 -> 1;
        a == 2 -> 0;
        else -> 3;
    };

A plain if/else expression with no else-if is still left alone.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
2. Docs: Generated documentation site header renamed to "Rell Docgen"

The documentation generator titled its output "Rell System Library API Reference", and the same header appeared
on documentation sites generated for libraries other than the system library. The site header (and the matching
page titles and breadcrumbs) now reads "Rell Docgen". Page URLs are unchanged: the output directory slug stays
pinned to the legacy "Rell System Library" name, so existing links keep working.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
3. Tools: Linter quick fixes are titled after the edit they make

A linter quick fix in the language server repeated the diagnostic message as its action title, so the editor
popup showed the problem statement twice ("Variable 'state' is never modified, so it can be declared using
'val'") and never said what applying the action would actually do. Each auto-fix now carries its own title
describing the edit, for example:

    Replace 'var' with 'val'
    Replace 'if' with 'when'
    Replace with 'xs.empty()'
    Replace with double quotes

Diagnostic messages are unchanged; only the quick-fix action titles differ.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
4. Tools: Linter diagnostics underline the offending code instead of one character

The language server published every diagnostic with an empty range, so editors highlighted only the single
character at the issue's position (for example, just the "i" of an if that could be a when). Linter diagnostics
now carry the real span of the offending code:

- rule_replace_if_with_when, rule_simplify_boolean_return and rule_simplify_nullable_if underline the if
  keyword of the reported conditional, following the IDE convention of marking the misused keyword rather
  than the whole multi-line construct;
- rule_constant_detection underlines the var keyword (or the variable name inside a tuple declarator, where
  the shared var cannot be rewritten);
- expression-level inspections (redundant boolean comparisons, .size() comparisons, quote style, unused
  variables and the rest) underline the whole reported expression or name.

Compiler errors and syntax errors still report a single position; widening those requires end positions in
the compiler and is unchanged for now.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
5. Tools: Language server honors the code-action kind filter

The code-action endpoint ignored the "only" kind filter of the request, so clients asking for quick fixes
alone still received the source actions ("Disable linter for this line", "Fix all auto-fixable issues").
IntelliJ requests quick fixes for a diagnostic and intention actions for the caret separately, so the same
suppression action appeared twice in the editor popup. The server now filters the returned actions by the
requested kinds (a requested kind also matches its sub-kinds), and each channel gets only its own actions.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
6. Tools: Quick fix to disable an inspection globally in .rell_lint

Every linter diagnostic now carries a second quick fix, "Disable '<rule>' in .rell_lint", next to the
existing per-line suppression. Applying it switches the whole rule off for the project: the server sets
"<rule>=false" in the .rell_lint file the linter actually reads (workspace root or up to two parent
directories), creating one at the workspace root with an [*.rell] section when none exists. The edit
runs server-side (workspace/executeCommand), so the linter options reload and the rule's diagnostics
disappear immediately, and repeating the action rewrites the existing assignment instead of appending
duplicates. Formatter diagnostics get the same action for their gating rule_formatter key.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
7. Tools: Language server accepts client-chosen settings files (chromiaConfigFiles)

The language server discovered its index roots by scanning workspace folders for files named chromia.yml,
so projects built with an alternate settings file (chr -s/--settings, e.g. atbash.yml) got no index root:
their compile.source and libs went unapplied and files fell back to single-file indexing. Clients can now
pass the settings files to use as the chromiaConfigFiles initialization option (an array of file URIs).

Registered files are merged with name-based discovery rather than replacing it (a client only knows about
the projects it scanned, so dropping discovery would unanchor the rest), and each one shadows the
chromia.yml of its own directory, so a project whose settings file is an alternate never anchors twice.
Each index root reads its Chromia model (rellVersion, compile.source, libs) from exactly the registered
file, including on watched-file changes to it and across a rename of its project root; cached index data
compiled under a different settings file is not reused. Unusable entries are logged and skipped instead of
failing initialize. Without the option, discovery behaves as before.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
8. Tools: Formatter keeps line breaks written at binary operators

A line break the author put inside an expression only survived in if and while conditions, and only around
and/or. Everywhere else the formatter pulled the operands back onto one line, so

    val b = null
        ?: 1;

reformatted to val b = null ?: 1; on save.

Such a break is now preserved wherever the expression appears, and normalized to the shape the and/or
wrapping already used: the operator moves to the start of the continuation line, indented one level. Both

    val b = null
        ?: 1;

and

    val b = null ?:
        1;

format to the first of the two. An expression the author wrote on one line is untouched, so

    val c = null ?: 3;

stays as it is.
