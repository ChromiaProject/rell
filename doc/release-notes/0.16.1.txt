RELEASE NOTES 0.16.1 (2026-07-15)

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
1. Docs: Anonymous extension functions excluded from generated documentation

The documentation generator no longer emits entries for anonymous @extend functions. An anonymous @extend body
compiles to an internal function#N name that cannot be referenced from Rell code, so the generated entries were
noise: they had no stable name to link to and no call site could ever use them. Named @extend functions are
documented as before.

@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@@
2. Docs: Layout fixes in generated documentation

Two rendering fixes in the generated documentation site:

- Numbered @see lists render as real ordered lists. Previously the leading "1." marker was mistaken for a link
  label, producing a bogus [1.] link followed by a redundant em-dash.
- Entity and struct fields without a doc comment no longer get the vertical gap that separates documented fields,
  so undocumented fields read as consecutive source lines.

3. Docs: Misc documentation-generator improvements

A few small fixes to the generated documentation site: syntax highlighting now covers JavaScript code blocks and
the -> operator (previously unstyled in Rell code blocks), and several stdlib doc comments were switched to the
```rell code-fence form so their examples get proper highlighting.

5. Library: Named arguments fixed for functions with multiple optional parameters

Named arguments to standard-library functions with several optional parameters - such as join_to_text - now bind
correctly in two cases that were broken:

- reordering by name on a method call was ignored:
  [1, 2, 3].join_to_text(prefix = '<', separator = '*') gave *1<2<3 instead of <1*2*3;
- skipping an earlier optional misplaced the value - a wrong result for [1, 2, 3].join_to_text(prefix = '<')
  (1<2<3 instead of <1, 2, 3), or a ClassCastException for join_to_text(transform = f).

6. Language: Lambda expressions

Rell now has lambda expressions: anonymous functions written with arrow syntax (->) that evaluate to first-class
function values. They can be stored in variables, passed to and returned from functions, and called like any other
function value.

    x -> x * 2                 // one parameter
    (x, y) -> x + y            // parenthesised parameters
    () -> 42                   // no parameters

The body is either a single expression (as above) or a value block whose trailing expression is the result
(return is not allowed inside a lambda - its result is the final expression):

    n -> {
        val doubled = n * 2;
        doubled + 1
    }

A parameter's type comes from one of two places: an optional explicit annotation, or the expected function type at
the use site (target typing). Annotations use the parenthesised form and are all-or-nothing - every parameter or
none. The return type is always inferred from the body.

    val f: (integer) -> integer = x -> x * 2;   // x is integer, from the declared type
    f(10);                                       // 20

    val g = (x: integer) -> x * 2;               // x is integer, from the annotation; g is (integer) -> integer
    g(10);                                       // 20

    function reduce(xs: list<integer>, f: (integer) -> integer): integer {
        var s = 0;
        for (x in xs) s += f(x);
        return s;
    }

    reduce([1, 2, 3], x -> x * x);   // 14

A lambda whose parameters are neither annotated nor typed by an expected function type is a compile error (a
parameterless lambda needs neither, having nothing to type).

Lambdas now fit many standard-library functions that take a function value. join_to_text maps each element
through a function before joining it; combined with a named argument, a one-line lambda supplies that function
without spelling out the intervening optional parameters:

    [1, 2, 3].join_to_text(transform = x -> "n" + x);   // "n1, n2, n3"

When the work needs several statements, a lambda with a value-block body replaces the partial application that was
previously the only option. try_call runs a function and traps any exception it throws:

    val result = try_call(() -> {
        val h = checked_div(20, 4);
        h * h
    });   // integer? - 25, or null if the call threw

A lambda captures each enclosing local variable it refers to by reading the binding's current value when the lambda
is created; reassigning that outer variable afterwards is not visible inside the lambda. This is a value capture in
the same sense as any Rell assignment, not a deep snapshot: a captured mutable object (a list, map, set, ...) is
captured by its reference, so an in-place mutation made to it after the lambda is created is visible inside the
lambda - only reassigning the variable is not. A captured variable is read-only inside the lambda.

    var n = 7;
    val g: (integer) -> integer = x -> x + n;
    n = 100;
    g(1);   // 8 - reassigning n is not seen; g read n's value (7) when it was created

    val xs = [1, 2, 3];
    val h: () -> integer = () -> xs.size();
    xs.add(4);
    h();   // 4 - xs is captured by reference, so the in-place add IS seen

The code formatter supports lambda expressions, including value-block bodies.

7. Language: Value blocks as if/when expression arms

An arm of an if or when expression can now be a value block - the same block form as a value-block lambda body:
zero or more statements followed by a trailing expression (no ;) that is the block's result.

    val x = if (cond) {
        val v = compute();
        v * 2
    } else fallback;

    val y = when (n) {
        0 -> 'zero';
        1, 2 -> {
            val s = 'small';
            s + ':' + n
        }
        else -> 'big'
    };

Only the chosen arm evaluates. A block arm has plain-code-block semantics - it runs inline, in the enclosing
function's frame:

- Enclosing local variables are visible and assignable, and nullability analysis flows through the block.
- return returns from the enclosing function. An arm that returns on all paths yields no value, and the
  conditional takes its result type from the other arms:

      val sign = if (n < 0) { return 'negative'; } else { 'non-negative' };

- break and continue inside a block arm bind to the enclosing loop.
- At-expression scope applies: attributes and the $ placeholder resolve inside a block arm of a
  collection-at projection.

The trailing expression (no ;) is the block's value; a block with statements only is unit-typed, which a
conditional arm cannot be (unless it always returns - such a block is bottom-typed, see section 7).

Semicolons in a when expression are unchanged for expression arms: an expression arm is terminated by ; (the last
case may omit it, as before). A block arm ends at its closing } and takes no ; - like a block in a when statement.
All previously valid code parses as before.

Restrictions:

- In expression positions with no enclosing body statement - an at-expression body, a parameter or attribute
  default value - return/break/continue cannot escape the block (there is nothing to unwind to); the block
  itself is fine.
- A value block cannot be used in a global constant's expression: its statements cannot be validated as
  constant, so blocks are rejected there.

8. Language: Jump expressions - return, break and continue as expressions

return, break and continue can now be used as expressions, in addition to their statement forms. A jump
expression never produces a value - evaluating it escapes the enclosing statement - so its type is an internal
bottom type that is assignable to every type and absorbed when computing a conditional's result type. The bottom
type cannot be written in Rell code; it only appears through inference.

This makes a bare jump legal exactly where an expression is expected, most usefully:

- As an if/when arm - including the trailing expression of a value block arm, which now needs no ;
  (consistent with the trailing-expression form of section 6):

      val a = if (b) { return 'early' } else null;
      val v = if (n < 0) return -n else n * 2;

- As the right operand of ?:, giving guard clauses; the elvis result type is the left operand's value type,
  and afterwards the left operand is smart-cast to non-null:

      function f(x: integer?): integer {
          val y = x ?: return -1;    // y: integer
          return x + y;              // x is known non-null here
      }

  This includes the fetch-or-return guard over an at-expression with @? cardinality - the jump
  evaluates after the query produced null, outside the at-expression body, so the result is the
  non-nullable row type:

      val u = user @? { .name == n } ?: return 'no such user';
      // u: user

- break and continue in loop bodies, binding to the enclosing loop:

      s += if (x < 0) break else if (x == 0) continue else x;

The return operand is greedy: everything to the right of return binds to it (x ?: return 1 + 2 returns 3).
In a when expression, a jump arm is an ordinary expression arm and is ;-terminated as before (section 6).

A jump expression follows the same placement rules as the corresponding statement: return stays prohibited
inside lambda bodies (its result is the final expression), jumps cannot appear where no enclosing body statement
or loop exists (at-expression bodies, parameter/attribute default values, global constants), and a bottom-typed
expression can never be part of a database at-expression's SQL.

A conditional whose arms all jump is itself bottom-typed, and the statements after it are dead code. Consuming a
jump expression's value where a value is actually needed - a call argument, a val/var initializer, a collection
literal element - compiles with a warning (expr:unreachable), since the value never materializes. Operands of
binary operators are not absorbed: 1 + (return 2) is still a type error.

Errors and warnings changed as a result. Code where every arm of an if/when expression returns, previously rejected
with expr_if_unit or when_exprtype_unit, now compiles (the conditional is bottom-typed); any statements following it
are reported as dead code (stmt_deadcode). Compile-error tests matching those codes may need updating. No previously
valid code changes its meaning.
